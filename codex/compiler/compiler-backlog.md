## COMPILER-55 -- OPEN, unowned (Steve Howell's issue 120, VERIFIED STATICALLY at head by blu 2026-09-07): a prose continuation indented to exactly THREE columns is lexed as CODE and joins the previous definition's expression

`Syntax/Parser.codex:1302` defines a prose line as `(current st).column == 2`,
exactly. The continuation tests are `column > 3`, at `:1316`
(`skip-prose-lines`), `:1400` (`collect-prose-with-text`) and `:1535`
(`parse-top-level`). Column THREE is neither: not a new prose line, not a
continuation, so it falls to the else and is returned as the start of code,
where it joins the preceding expression.

No guest was spent. The three call sites read as written above, and the gap is
arithmetic on the two constants rather than a claim about behaviour.

The fix is a decision, not a patch: either the continuation test becomes
`column > 2` (prose owns everything past the marker column) or the parser
refuses column 3 with a diagnostic. Both change what an existing corpus means,
so this wants a ruling before code. Steve's reproducer is three files differing
only in the indent of the continuation line.

FIRST MEASURED BITE (root, 2026-09-08, the Update 56 release gate): `check-errors`
went red on `codex/test/errors/unit-field-assign` because a three-column prose
line in it lexed as code and main 22739's CDX0008 fired on the `''` inside the
sentence. blu rewrote the test's prose; the defect above is unchanged and is
what the row still names.

## COMPILER-56 -- OPEN, unowned (Steve Howell's issue 126, routed by blu 2026-09-07, NOT verified on metal): the hosted compiler types every comparison EXPRESSION `ErrorTy` where bare metal says `boolean`

Measured by Steve against a tree that ALREADY CARRIES PR 117, so this is not a
regression of PR 117's fix and not closed by it. Six operators (`lt le gt ge eq
ne`) come back `error` from a hosted `codexir` and `boolean` through the seed,
with the IR otherwise identical. He states the qualifier himself: for `fib` the
emitted zig is byte-identical either way, so on that evidence the wrong type is
inert for codegen. PR 117's own history is the argument for not shrugging: there an ErrorTy binding cascaded until nine ladder rungs went red off one cause.

TWO CANDIDATE SITES ELIMINATED BY READING (blu, no guest): the whole `mcopy`
memo apparatus is unreachable on a hosted target after PR 117.
`check-batch-copy` is called only from `check-batch-close`, which now returns
early on `hosted-kind /= 0`; `tcons-lookup` (`Types/Unifier.codex:932`, the
only other raw-memory read in the type layer) is reached only through
`mcopy-text-content`, which is inside that same family. So the site is neither
the copier nor the memo, and whatever answers `ErrorTy` for a comparison
expression is somewhere else.

Verifying further needs a hosted build, which is why this routes rather than
resolves.

## COMPILER-57 -- OPEN, unowned (Steve Howell's issue 125, routed by blu 2026-09-07, NOT independently measured): 10 of 120 ordinary Real literals land one ULP from correctly rounded, in the front end

His measurement: 120 random doubles in (-1000, 1000), each written as its
shortest round-tripping decimal, compared through `real-to-bits` because `show`
on a `Real` is refused. An independent Rust front end gets 0 of 120 wrong;
Codex gets 10, worst gap 1 ULP. Every COMPUTED value in his two failing test
chapters is bit-identical across arms, so this is the literals and not the
arithmetic.

THIS IS THE ROUNDING HALF ONLY. The WRAP half of the same `__text_to_double`
-- past 19 digits the decimal accumulator wraps in one i64 -- was COMPILER-37,
and it is FIXED: a literal wider than an i64 is refused with CDX2073 rather
than read as a different number (main 21199, shipped in Update 54). The
refusal is pinned by `codex/test/errors/real-literal-overflow.codex` with a
`.failing` sidecar, and that chapter's own prose names Steve Howell's issue
106. COMPILER-37's row is absent because this register DELETES a closed entry,
which is its stated convention and not a lost row.

`codex/test/ops/real-literal-rounding` guards this half with twelve values all
below ten, so it is structurally blind to the 1-ULP cases. The coupling that
made Steve file rather than patch still holds: the zig plug's
`zig-p-cx-text-to-double-bits` mirrors the seed deliberately, so both parsers
move together or neither does.
