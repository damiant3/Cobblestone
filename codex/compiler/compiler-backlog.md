| COMPILER-1 | **Runtime scope enforcement for effect grants** | Re-homed from CAPABILITY-REFINEMENT step 6 (moved to Done 2026-08-05). Compile-time scope enforcement is shipped and pinned (`lint-effect-scope` / `scope-grants` in the type checker; `codex/test/errors/scope-violation`, `scope-network-port`). **Correction 2026-08-11 (val): the earlier claim that "the runtime half was never built" is FALSE, verified against source.** Runtime scope enforcement IS built and sound on x86-64 for FileSystem (path prefix) and Network (host:port authority), and the effect-op path enforces the SCOPE, not just the cap bit. Read path: `__fs-read-servicer` (checks `cap-filesystem-read`) -> `fat16-servicer-read` -> `fat16-read-text` -> `fat16-read-bytes` -> `fat16-resolve-path`, which calls `fat16-scope-admits` reading `process-get-scope process-get-pid` (the CALLING process's scope; the servicer runs in-context, only flipping the elevation flag). Writes are symmetric via `fat16-create-file` (`fat16-create-directory`, `fat16-list-root`, `fat16-root-entries` gated too); network via `net-scope-admits` in `http-request` / `fetch-tls`. Scope is serialized into the CDX (`manifest-cap-bytes`: cap-id, direction, scope-len, scope-bytes) and loaded into the proc table (`proc-scope-offset` fs, `proc-net-scope-offset` net) on BOTH boot (`emit-set-boot-scope`) and verified-load (`ProcessCaps.apply-load-decision`); the load-time wiring is pinned by `loader-scope-test`, `loader-network-scope-test`, `process-caps-test`, `network-scope-{open,deny,spawn}`. **Real remnants:** (1) **ARM64 has no counterpart.** The whole process/capability kernel is absent on ARM64 (no proc table, no syscalls, no fs/net execution), so scope is silently unenforced there. This is a MAJOR effort and its own initiative, not a COMPILER-1 tail; a QEMU bed now exists. Full detail and the parity chain are tracked in `codex/plugs/plugs-backlog.md` 1.10. (2) **Runtime denial IS tested end-to-end (correction 2026-08-11; the earlier "no denial test" claim here was wrong, caught by reading the tests).** `scope-runtime-deny` boots a program granted `FileSystem.Read "OK"` on a real disk and asserts the out-of-scope write (False), read (<none>) and root listing (0) are all refused while in-scope ops succeed (re-run green here, seed AF4E14D9); `scope-runtime-spawn` asserts a spawned child inherits the scope and denial (10); `scope-runtime-open` is the no-scope control; `loader-scope-test` asserts the verified-load path installs the scope. No denial-test gap remains. The only combination not in a single test is a verified-load-NARROWED scope plus a runtime out-of-scope read in one program; it is covered compositionally (same `proc-scope-offset` cell, same `fat16-scope-admits`), and a composed integration test would be real but marginal. (3) **Architecture, revisit ONLY if it becomes structurally limiting (Damian ruling 2026-08-11):** enforcement is library-level -- the servicer routes through the gated `fat16-*` functions rather than the stub checking the path itself. There is no single chokepoint (`Fat16.codex:1073-1077` warns a new disk-reaching door needs its own gate), so a future ungated door is a silent hole with no test to catch it. A syscall-boundary chokepoint would collapse the N gates to one, but is a seed-affecting change that stays redundant with gates that must remain for direct in-process callers. KEPT AS-IS: the burden is a clarity/discipline cost, not a structural break. Not blocking anything current. |

| COMPILER-5 | **A BARE hex literal past i64-max in argument position does not round-trip through the text emitter** | The `disk-build-fnv` site that motivated this is FIXED (val, main 15410): the FNV-1a offset basis is now the parenthesized natural constant `(#CBF29CE484222325)`, replacing reek's `(0 - 3750763034362895579)` workaround, seed rebuilt 55983566. **The original diagnosis ("the fix is in the lexer or the text emitter") was WRONG and is corrected here so nobody re-chases it: there is NO emitter bug.** The sem-equiv normalizer (`build/compare-codex-semantic.ps1`, `Normalize-OpAliases`) already converts every hex literal to `- <decimal>`, so hex and decimal are equal to the gate. A negative `IrIntLit` (which only a hex-past-i64 literal produces; a decimal `-N` is a folded `Negate`) emits as `(-N)`, parenthesized by `needs-parens`, and round-trips. The residual: a BARE hex literal as an argument, `f #CBF...`, is legal but normalizes to `f - N` (no parens) while the emit is `f (-N)` (parens), so they disagree. Parenthesizing the source, `f (#CBF...)`, closes it -- which is what the disk-fnv fix does. A general fix would teach the normalizer to reconcile `( - N )` with `- N`, a `build/` generator change, not a compiler change. Latent and niche: no bare hex-past-i64 argument exists in the tree today. |
