| GPUSHOW-2 | **`real-cos 0.0` is wrong by 5.6e-8, and the arm that grades it has a tolerance just above the error** | From Steve Howell's issue 122, verified statically at head by blu 2026-09-07; no guest spent. `codex/foreword/gpu/DeviceMath.codex` evaluates `real-cos (x) = dm-sin-poly (dm-fold-quadrant (dm-reduce (x + dm-half-pi)))`, so `cos 0` becomes `sin (pi/2)` -- and `pi/2` is the LARGEST argument `dm-fold-quadrant` can produce (`:58-61` folds anything above `dm-half-pi` back down), so the one input every caller writes first lands on the 11th-order Taylor series' worst point. His arithmetic: the next term there is `(pi/2)^13 / 13! = 5.692e-8` against a measured error of `5.626e-8`, so truncation is the whole cause. **WHY NO ARM SEES IT:** `codex/test/lib/device-math.codex:69` grades exactly this call, `near (real-cos 0.0) 1.0 tr-tol`, and `tr-tol` is `0.0000001` (`:31-32`). The error is 56 per cent of the tolerance, so the arm passes while carrying the defect -- a threshold set just above the effect returns a null that reads as an all-clear (L-THRESHOLD). Tightening `tr-tol` without fixing the series turns this red on a shipped chapter, so the two move together. Consumers are kernels: `SimKernels`, `MonteCarloSim`, `TransientAnalysis`, `WaveformViewer`, `FireworksSimKernel`. Routed here because the subject is a foreword GPU chapter and there is no `gpu-backlog`; if that is the wrong home the row wants moving, not re-deriving. |
