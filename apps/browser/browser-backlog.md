# Browser -- open capabilities

App-domain backlog. There is no platform-wide register any more:
`docs/PM/BACKLOG.md` was deleted 2026-07-23 and must not be recreated.
`docs/PM/CurrentPlan.md` carries the shape and the priority order for
the platform. Anything that is this application's own behaviour lives
here.

The rules are the same ones: an entry says what is still missing and
nothing else, a closed entry is DELETED rather than annotated, and a
gap that is still real is never quietly dropped.

**BROWSER-3 was deleted 2026-08-11 because it was never real.** It claimed
no test exercised a repaint after the first, on the evidence that four
injected arrow keys changed nothing while codex-vm logged
`HID: first key event sc=50` for an injected 80. **That trace prints the
scancode in HEX**: `0x50` IS 80, so the key was delivered correctly and the
entry's own suspect was innocent. The page simply has nothing to scroll --
the other branch of the disjunction the entry left open, which one look at
the log's base would have closed. Measured instead with Ctrl+T
(`-keys 29,20,157`, and identically through a `-keys-file` timeline): the
tab bar gains a second tab and the repaint is correct, so keyboard input
reaches the browser AND a frame rendered after a `__heap-restore` is sound.
Recorded here rather than dropped silently, because the lesson is about
reading an instrument, not about the browser.

| BROWSER-5 | **The page is clipped at the viewport and cannot be scrolled into; the tree still overflows the pane by 138 device pixels** | **The out-of-bounds write is FIXED (2026-08-20).** It was real and it was the reason this row stopped being cosmetic: with the pane open, `-hwwatch` fired at rows 950, 960, 970, 976 and 977 of a 900-row framebuffer, every one `writer=0x1084c0` (`gop-put`) carrying `now=0x101010`, the page background, for 78 rows and 499,200 bytes on every paint. `comp-render` now clips to the box it was given and the same watchpoints answer zero while the control at row 0 still fires six times. The account of the clip is `apps/works/works-desk-contract.md` 5.1 and the arm that fails without it is `codex/test/gop-composite-vclip`. **What is left is the layout, and it is unchanged:** `codex/test/apps/browser-pane-fit` still reports the tree reaching 982 against a granted 844, because the fix bounds the PAINT and not the layout. The viewport is `widget-set-flex viewport 1` and `flex-col-place` gives a flex child `box-max mh share`, so a content minimum larger than its share still wins. The page is therefore truncated at the viewport with no way to reach the rest, and `ScrollState` exists per tab with `scroll-by` and `scroll-page-up/down` wired but nothing offsets the tree by it. That is the remaining work: a viewport that scrolls, and `desk-bro-h` corrected to the measured band (it grants 844 where the band begins at 828) once something carries the laid-out root into `desk-step-of`. Found by val 2026-08-19 as a 12-row jump; re-measured at 68,728 pixels in y 828..883 at 1600x900. **The arithmetic half is FIXED and was a different defect:** `load-new-tab-content` built the page at `vh - chrome-height`, which omits the root panel's inset and the margins between the bars, so at 1024x768 the page was built for 684 and given 658. It is measured now (`browser-viewport-h` lays the chrome with an EMPTY viewport), and `codex/test/apps/browser-viewport-fit` pins built-for against given at 0. **The remaining half is now measured too, and it is a LAYOUT question after all.** `codex/test/apps/browser-pane-fit` reads it out of the tree with no capture involved: the taskbar band is at device 828..883, `desk-bro-h` grants the pane 844, and the laid-out browser tree reaches 982. Two independent errors. (1) `desk-bro-h` is `h - dk-task-h * ui-wscale w`, which assumes the band is flush with the bottom of the screen; the root panel's padding leaves 8 logical rows below it, so the band starts 16 device pixels ABOVE where that arithmetic says, and `desk-taskbar-hit.expected` has recorded those 8 rows since it was written. (2) the chrome root is correctly `y=0 h=422` logical and its third child is `newtab y=101 h=390`, 69 logical rows past its own parent, with only 321 left. The viewport is already `widget-set-flex viewport 1`, so **a flex child is not being shrunk below the minimum its content declares** -- the WORKS-45 sizing rule seen from the other side. That is what paints page pixels down to device 899 and erases the band on every repaint; `desk-browser-open` pokes `desk-second-cell` to -1 so `desk-clock` redraws it once after the first paint, and `gbr-step` does not, which is the whole of the visible jump. **Do not spend a day on the units theory:** the pane is measured in device pixels and the tree is laid out in logical ones, and the control arm in that test initialises the same pane in logical pixels and gets a byte-identical tree, so the dimensions handed to `browser-init` do not drive the overflow. **And the obvious fix is INERT, which is the last thing that test says.** Shrinking the flex child to its 321 share looks like the repair and moves nothing: the deepest node in the whole tree IS `newtab` itself, so its children fit inside its 390, and clamping it to 321 pushes them out by the same 69 one level down. Nothing in the widget layer clips a node to its box -- `Browser.codex` says so in its own prose above `browser-viewport-box` -- so a clamp anywhere just moves which node overflows. The bounding fix is CLIP-RECT SUPPORT in `comp-walk` plus a viewport that scrolls, and `ScrollState` already exists per tab with `scroll-by` and `scroll-page-up/down` wired. That is a capability the compositor does not have and is the real size of this row. `desk-bro-h` is worth correcting alongside it and not before: it needs the laid-out band, which `desk-step-of` does not currently carry, so it is a thread-`root`-through change or a `ds` cell computed at open, not a one-liner. |
| BROWSER-4 | **A named host is not reachable, and `resolve-and-load-remote` is uncalled** | Made explicit 2026-08-11 (blu) on Damian's instruction, and it is a narrowing of the DEFAULT path rather than a new limitation: remote loading has never been demonstrated to work on any runtime here, and `load-page-source` already answered `SourceAddress` with "Network loading requires Phase 2". `resolve-and-load` now handles `LocalAddress` and `HashAddress` and answers a `NamedAddress` with a PageFetchError naming the host. That is what lets the entire browser carry NO Network effect, which is what lets `GopDesk` embed it without the desktop's type claiming network reach (WORKS-10). **The wire path is kept by name, not deleted:** `resolve-and-load-remote` and `load-by-address-remote` route a `NamedAddress` to `load-remote-page` -> `fetch-page-tcp` exactly as before. **Nothing calls them**, so they are pruned from every binary and are UNCALLED CODE in the L-UNCALLED sense -- they compile and nothing executes them, so they can rot silently. Whoever lands Phase 2 should call them from a build that wants the wire and should not assume they still work. `codex/test/apps/browser-offline-load` pins both arms, and its real guard is that the chapter declares `[Console]` alone: rewiring the named arm makes `resolve-and-load` effectful again and the test STOPS COMPILING (CDX2031) rather than passing quietly. |
