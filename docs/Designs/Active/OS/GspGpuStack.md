# Our own GPU stack on the GSP firmware

*Owner: reek (stage 0, root 2026-09-30). Campaign: `docs/PM/CurrentPlan.md`,
"GPU compute on our own OS is the GSP firmware route" (Damian, 2026-09-30,
tier 1).*

## The requirement

One GPU stack of our own drives the RTX 4060 Ti (Ada, AD106) through
NVIDIA's GSP firmware. It has no NVIDIA driver, no NVIDIA user-space library
and no vendor compiler, and it serves every GPU user in order:

1. general compute (the diffusion kernels the PTX plug emits today),
2. tensor cores for the diffusion engine (WORKS-3, the desk's Generate),
3. the desk's 3D rendering on metal (WORKS-80),
4. last, `nvcuda.dll` behind codex-vm's GPU bridge (ops 40 to 48,
   `codex/os/kernel/GpuBridge.codex`).

This supersedes `docs/Designs/Done/OS/GpuCompute.md`'s "hard block": that
design named the route (load the GSP-RM image from disk, as nouveau does)
and stopped at it.

## What the firmware requires of a driver

The firmware is signed. Our code never runs on the GPU's security
processors; it arranges memory, hands the signed images to them, and then
talks to GSP-RM over shared memory.

**Files** (linux-firmware `nvidia/ad102/`, which `ad106` links to; the box's
Windows driver store holds a `gsp_ga10x.bin` too, but the booter files must
match the GSP image's version, so the linux-firmware set is the one used): the GSP
image `gsp-570.144.bin` (63,571,696 bytes, from NVIDIA's 570.144 driver
package), `bootloader`, `booter_load`, `booter_unload` and `scrubber`.
nouveau prefers 570.144 and falls back to 535.113.01
(`nvkm/subdev/gsp/ad102.c`, `ad102_gsps[]`).

**Boot chain**, in nouveau's order (`tu102_gsp_oneinit`, `r535_gsp_oneinit`,
`tu102_gsp_init`, `r535_gsp_init`):

1. Lay out framebuffer memory and carve WPR2 top-down: the FRTS region, the
   boot binary, the ELF image, the GSP heap, and `GspFwWprMeta`.
2. Build a three-level page table in system memory over the GSP image.
3. Build the LibOS arguments and two 256 KiB message queues, and queue the
   system-info (RPC 72) and registry (RPC 73) messages before GSP runs.
4. Extract FWSEC from the card's **VBIOS** (the PMU table, ucode type
   `0x85`), patch it with the FRTS command (`0x15`) and run it heavy-secure
   on the GSP falcon. It establishes WPR2 (`nvkm/subdev/gsp/fwsec.c`).
5. Put the GSP core into RISC-V mode and run `booter_load` on the SEC2
   falcon with the WPR metadata address in its mailboxes.
6. Wait for the `GSP_INIT_DONE` event (`0x1001`), serving
   `GSP_RUN_CPU_SEQUENCER` (`0x1002`) register programs on the way.
7. Fetch static info (RPC 65) and the interrupt table, then enable
   interrupts.

**Interface after boot** (`nvkm/subdev/gsp/rm/r535/rpc.c`): 4 KiB queue
elements with a 48-byte header (an XOR checksum, a sequence number) and an
RPC header (`'CPRV'`, function, length). A write is followed by a doorbell
(`0xc00` on the GSP falcon). Objects are made by `GSP_RM_ALLOC` (RPC 103)
and driven by `GSP_RM_CONTROL` (RPC 76), in the order `NV01_ROOT`,
`NV01_DEVICE_0`, `NV20_SUBDEVICE_0`, `FERMI_VASPACE_A`,
`AMPERE_CHANNEL_GPFIFO_A` (`0xc56f`), `ADA_COMPUTE_A` (`0xc9c0`).

**What stays ours:** GPU page tables (GMMU) and their registration, BAR1 and
BAR2 mappings, a channel's instance, USERD and RAMFC memory, the graphics
context buffers and their promotion, the GPFIFO ring and doorbell, fences
(semaphore methods), and the top-level interrupt tree. GSP-RM owns engine
init, power management and fault reporting.

## Code generation is the larger half

The firmware runs nothing we write. Every kernel must reach the card as
**SASS**, the native instruction set, and today the PTX plug's output is
turned into SASS by the JIT inside `nvcuda.dll`. So "no vendor DLL" means
our own SASS back end for SM 8.9.

- **The encodings** are not published by NVIDIA (it documents mnemonics
  only). NAK's `sm70_encode.rs` (4,846 lines, MIT) holds encodings for SM
  7.0 to 8.9, established against `nvdisasm` and hardware tests.
- **The scheduling bits.** Each SASS instruction carries stall counts,
  yield and dependency-barrier fields that the hardware trusts. A wrong
  value is a silent race, not a fault, so this is where the back end needs
  its strongest arm.
- **Tensor cores.** NAK emits HMMA (F16 in, F16 or F32 accumulate; m16n8k8,
  m16n8k16) and IMMA (m8n8k16, m16n8k16, m16n8k32), and no FP8 (QMMA). The
  diffusion path needs only F16 HMMA: its FP8 weights are dequantized to
  f16 in shared memory and run the existing WMMA (`Diffusion.md`, "Fitting
  16 GB").

The back end is a new plug (IR or PTX-level input to SASS output), beside
`codex/plugs/ptx`.

## The second target: the GTX 970

GM204 (Maxwell 2, `10de:13c2`) has no GSP, and it still needs NVIDIA-signed
firmware for graphics and compute. nouveau brings up GR on it only by
running the signed ACR image on the PMU falcon, which then boots the signed
FECS and GPCCS context-switch processors in light-secure mode
(`nvkm/subdev/acr/gm200.c`, `nvkm/engine/gr/gm200.c`; without them
`gm200_gr_nofw` gives up). The firmware set is linux-firmware
`nvidia/gm204/` (`acr/` and `gr/`, 15 files, about 70 KB).

Everything else is the driver's own, as nouveau writes it: FIFO, runlists
and channels (`MAXWELL_CHANNEL_GPFIFO_A`, `0xb06f`), the MMU and page tables,
instance memory and the GR context. That is more of the driver than on Ada,
where GSP-RM owns engine init. The compute class is `MAXWELL_COMPUTE_B`
(`0xb1c0`), launched as both of Mesa's drivers launch it: a QMD in NVIDIA's
V00_06 layout (`cla0c0qmd.h`) through `LAUNCH_DESC_ADDRESS` and `LAUNCH`
(gallium `nve4_compute.c`; NAK `Qmd0_6`). V01_07 is NVIDIA's own, and no
open filler exists to grade it against. nouveau has no clock
control for GM20x, so the card runs at the clocks its VBIOS leaves.

**Why the 970 is useful:** its SASS (SM 5.2) is the best mapped of any
NVIDIA generation. maxas documented its control codes, and Mesa has two
independent encoders for it (`nv50_ir_emit_gm107.cpp`, NAK's `sm50.rs`).
The first SASS back end is therefore SM 5.2, and SM 8.9 follows it.

## What builds and grades now, with no GPU run and no vendor tool

Each instrument is foreign, and each says what it can falsify:

| instrument | falsifies |
|---|---|
| NVIDIA's published register references (`open-gpu-kernel-modules` `src/common/inc/swref/published/maxwell/`, `ada/ad102/`) | register offsets and field bits our driver writes |
| NVIDIA's class and QMD headers (`cla0c0qmd.h` for Maxwell, as vendored in Mesa; `clc9c0qmd.h`) | method offsets and QMD field packing |
| Mesa's QMD fillers (`nak_fill_qmd`, `nve4_compute_setup_launch_desc`) for the same launch | our QMD, byte for byte |
| envytools' `envydis` (`gm107.c`), an independent decoder | opcode and operand bit placement of our SM 5.2 encoder |
| the scheduling-word layout, published by both maxas and NAK | how our encoder packs stall, yield and barrier fields (the two disagree on the yield bit's polarity; hardware settles it) |
| nouveau's GSP header excerpts and tinygrad's generated r570 structures | our GSP struct sizes, offsets and RPC numbers |
| tinygrad's pinned SHA-256 of the 570.144 firmware | that the files we load are those files |

None of these runs a kernel. What a kernel computes is proven only on the
card, in a window or a sitting.

## Stages

- **0**, this design, read naive. Landed; this revision follows the rulings.
- **1, the SM 5.2 back end**, in `codex/plugs/sass` (plugs take no token).
  The maxas oracles are cloned to scratch, never into the depot; each has an
  in-tree script under `build/` that writes a `codex/test` subject's
  `.expected`, run by Git for Windows' `perl.exe`
  (`C:\Program Files\Git\usr\bin\perl.exe`, not on PATH).
  - **The encoder**, `SassCtrl.codex` and `SassEncode.codex`: encodings
    from Mesa's `nv50_ir_emit_gm107.cpp` and NAK's `sm50.rs`, graded
    against maxas's own `genCode`, `readCtrl`/`printCtrl` and `XMAD.LO`
    expansion (`build/sass-ctrl-oracle.ps1`, `build/sass-encode-oracle.ps1`),
    each with a sabotaged field as control. It covers the forms a first
    kernel needs, the 64-bit carry chain included. The yield bit is stored
    raw; which value means yield is a hardware question (unknown 10).
    envydis joins as a second decoder once its build route is ruled: it is
    C, and MSVC 14.44 is installed (Visual Studio 2022, `vcvars64.bat`), so
    a native Windows route exists beside WSL; it is untried.
  - **The plug**, `SassLower.codex`, `SassSched.codex` and `SassPlug.codex`, run by `codex/plugs/sass/run.ps1`. Input is the PTX plug's wire (`compile.ps1 -IrCce
    -Passes text-plug`, parsed by `parse-ir-chapter`); output is a
    maxas-syntax listing, control notation on every line, and the words.
    - **Scope of the first slice.** Entry definitions are chosen as the PTX
      plug chooses them (a `gpu-` name). Helper calls are inlined, as the
      PTX plug inlines them; recursion is refused. Handled: Integer add,
      subtract, comparison, multiplication by a power-of-two constant (a
      shift), `if`, `thread-idx-x`/`block-idx-x`/`block-dim-x`, and
      `device-load`/`device-store`, whose index is scaled by 8 as in the
      PTX plug. Refused: Real, the narrow and float load and store
      variants, division, remainder, and any other multiplication, because
      a 64-bit multiply built from XMAD cannot be graded for what it
      computes before stage 4.
    - **Integer** is a register pair, the low word in the even register,
      64-bit two's complement without an overflow trap, as the PTX plug's
      `.s64` is; arithmetic runs through the carry chain (IADD.CC/.X,
      ISETP.X, SHF).
    - **`if` is predicated, not branched:** an ISETP pair sets P, one arm
      runs under `@P` and the other under `@!P`, so no divergence handling
      (SSY/SYNC) and no BRA are needed while both arms are straight-line.
    - **Constant bank 0 is our layout**, filled by our own driver at stage
      4: block size x, y, z at 0x0, 0x4, 0x8 and grid size at 0xc, 0x10,
      0x14 (32 bits each); parameter i at 0x140 + 8 i, low word at +0, high
      word at +4.
    - **Control codes are conservative.** Each fixed-latency instruction
      stalls for its class latency in maxas's tables (`MaxAsGrammar.pm`:
      x32 and shift 6, cmp 13); S2R and LDG set a write barrier that their
      first reader waits on; STG sets a read barrier that the next writer of
      its registers waits on; yield is raw 1 (maxas `-`); reuse flags are 0.
    - **The grade**, `codex/plugs/sass/test-maxas.ps1`, rebuilds the plug,
      lists `codex/plugs/sass/test/first-slice.codex`, and runs every
      listing line through maxas's own `processAsmLine`, `readCtrl` and
      `genCode` (not `Assemble`, which wants a cubin), packing each group of
      three control codes with maxas's `Assemble` expression; every
      instruction word and control word must match the plug's, and the
      out-of-slice kernels must be refused by reason. The controls are a
      sabotaged encoder field and a sabotaged control-code field in the
      plug build. A sabotaged lowering is not a control: it still
      assembles to its own words. What a kernel computes is not graded
      before stage 4.
    - **Instruction accumulation:** each emit prepends an immutable node;
      kernel completion reverses and collects the instructions once. Emit
      heap/time is constant; construction and conversion are linear in
      instruction count. `test/emit-cost.codex`, run by `test-maxas.ps1`,
      checks instruction order, independent state forks and allocation growth.
      Measured 2026-09-30 with seed `B3256BF8B4CC8327`: 1,024/2,048/4,096/8,192
      emitted instructions used 163,984/327,824/655,504/1,310,864 bytes,
      including conversion and checking. The former copied-list path used
      4,362,360/17,113,208/67,780,728/269,779,064 bytes and fails the new
      allocation ceiling. Three whole-probe runs, including VM and harness
      startup, took 1,207-1,237 ms before and 540-575 ms after; these are not
      isolated emitter timings. Each new guest timing was below one timer
      tick, so timing does not establish a scaling curve. The first-slice
      listing is byte-identical and passes maxas.
    - **Remaining cost limits:** scheduler control-code accumulation
      (`SassSched.sched-step`) and listing text accumulation
      (`SassLower.sass-listing-groups`) still copy growing prefixes. The
      instruction-accumulator proof does not establish linear whole-plug cost.
  - **No cubin.** Our own driver loads kernels at stage 4, so an sm_52
    cubin would serve only NVIDIA's loader and the vendor tools, one ruled
    out and the other deferred (root, 2026-09-30).
- **2, the SM 8.9 encoder** the same way against NAK's encodings and Ada's
  published headers; HMMA F16 for the diffusion engine's WMMA kernels. The
  executable oracle is turingas (Python), not a native Rust build of NAK
  (Damian, 2026-10-01: "turningas is fine").
  - **First raw encoder slice:** `codex/plugs/sass/Sass89Hmma.codex`
    packs F16-input HMMA m16n8k8/m16n8k16 with F16 or F32 accumulation,
    guarded by P0..P6 or PT, and three source reuse bits. Scheduling fields
    are raw bits; barriers are 0..5 or 7 for none. Register indices are
    encoded, not a proof of fragment allocation or alignment. The SM 5.2
    plug driver remains unchanged; SM 8.9 lowering and other instructions
    remain open.
  - **Reference boundary:** Mesa 26.2.4 `sm70_encode.rs`, `OpHmma` and
    `set_instr_deps`, provide the SM 8.9 fields. Source SHA-256:
    `A6691B6B66E4C38B6EEEEC8D44AF99D89E80C7A1FD16A6AE13BDA5CD2D9393A3`.
    [NVIDIA's Ampere/Ada instruction list](https://docs.nvidia.com/cuda/cuda-binary-utilities/index.html#nvidia-ampere-gpu-and-ada-instruction-set)
    names HMMA; it does not publish those encoding fields.
  - **Executable grade:** `build/sass89-hmma-oracle.ps1` runs unmodified
    [turingas](https://github.com/daadaada/turingas) at
    `f7c1a74ebe6bc2ac51920b0fee29e27767f81724`, using its `ProcessAsmLine`
    and `GenCode` directly. The CLI lists SM70/75/80/86, not SM89; this is
    shared-instruction word agreement checked against NAK's SM89 path,
    not an Ada executable or hardware oracle. No cubin is produced.
    `sass89-hmma-turingas` compares 128 word pairs, including isolated
    field sweeps; `sass89-hmma-refuse` pins the narrower admission contract.
    The word order follows `cubin.GenerateText`: turingas's high integer
    half is the first little-endian word. Wait masks are decimal and
    two-character padded, stalls hexadecimal, and raw yield zero is `Y`.
    Grade a fresh oracle output against the `.expected` fixture with exact
    text equality after CR normalization before accepting the Codex test;
    the ordinary test alone consumes a static fixture. Opcode and control
    field sabotages must differ while still emitting all 128 valid rows.
  - **Limits:** fourth reuse-bit coverage, BF16/TF32, register-fragment
    layout, numerical answers and scheduling hazards are not graded here.
    The encoder uses bounded arithmetic and one result allocation per
    instruction, with no growing accumulator. Hardware remains gated.

  Host firmware-data helpers are separate from that acceptance:
  - `NvFirmware.codex` selects `.fwimage` and the requested chip signature
    from ELF64 little-endian RISC-V containers with ordinary section
    headers. Results are bounded spans borrowing the caller's buffer, not
    payload copies. `codex/test/nv-fw-elf` and `build/nv-fw-elf-oracle.ps1`
    run tinygrad c3aec477's original `elf_loader` and `init_gsp_image` with

  - The same chapter reads the r570 RISC-V bootloader descriptor and SEC2
    booter-load patch plan, and constructs a patched image in one new raw
    buffer. `codex/test/nv-fw-booter` and `build/nv-fw-booter-oracle.ps1`
    grade fields and complete patched bytes against original
    `init_boot_binary_image` and `prep_booter`. Parsers have fixed cost;
    construction is linear in image size. The caller owns both input and
    output lifetimes and selects/verifies firmware identity separately.
  - `NvFwsec.codex` locates FWSEC through the PCI ROM chain, BIT Falcon data
    and ucode table, then parses descriptor v2 or v3. The last matching
    application entry wins, as in tinygrad. `codex/test/nv-fwsec` and
    `build/nv-fwsec-oracle.ps1` distinguish their references: original
    tinygrad common lookup and v3 handling; original nouveau v6.12
    `nvkm_gsp_fwsec_v2`, stopped before firmware I/O, for v2 interpretation.
    Tinygrad has no v2 implementation at that pin. Fixtures cover six/eight

    fields and v3's last signature selection. Traversal retains scalar
    state and fixed-size results; it makes no firmware payload copy.

  the foreign implementation rejects those inputs. All oracle firmware
  inputs are synthetic. Actual firmware is read from the box only and is
  never downloaded or copied into the depot by these tools. These proofs
  do not establish real-firmware compatibility, authentication, full ELF
  conformance, FWSEC command-image construction, DMA, GSP startup or GPU
  execution.

    rejected before I/O. The sequence is SET_SYSTEM_INFO and
    SET_REGISTRY, FWSEC/FRTS, WPR2 check, GSP RISC-V switch and LIBOS
    mailboxes, SEC2 booter, active-core check, INIT_DONE and BAR1 reset.
    Inputs are prepared, pinned images and initialized queues. Synchronous
    callbacks expose numeric MMIO, microsecond delays, masked polls and
    RPC payloads/events; transports own deadlines and interleaved events.
    `codex/test/nv-gsp-boot` and `build/nv-gsp-boot-oracle.ps1` compare full
    ordered traces against tinygrad c3aec477's original NVDev initialization,
    Falcon methods, wait logic and generated register tables on logging
    stubs. Fourteen profiles cover alternate reset/start branches, DMA
    sizes, busy polling, device-status failures, event timeout and backend
    write/send/delay refusal. A swapped-RPC-order control is rejected.
    Exact compiled traces passed with seed `561EEBFC3ED59D96`; coverage is
    not exhaustive. Scripted clock/read responses do not calibrate deadlines.
    PCI discovery/reset, MMU setup, firmware preparation/authentication,
    physical queues and transport framing remain outside this proof.
    Golden-context creation is the stopping boundary after INIT_DONE.
    Hardware acceptance and a complete driver remain open.
- **6, the diffusion engine on metal** (ops 40 to 48 served by our driver),
  graded by the diffusion tests' `.expected`.
- **7, display and 3D** on both cards, designed at its own stage.
- **8, `nvcuda.dll` retired** from codex-vm.

## What it costs

The prior art sets the scale; the estimates are ours and unmeasured.

- The 4060 Ti's GSP boot, RPC and one channel: tinygrad does it in about
  1,700 lines of Python; in Codex, 4,000 to 6,000 lines.
- The 970's driver is larger than the GSP client, because it owns FIFO, MMU
  and GR context itself (nouveau: `fifo/gk104.c` 726 lines, `acr/` 2,172,
  `gr/gf100.c` 2,274, `ctxgf100.c` 1,471).
- The encoders: NAK's `sm50.rs` is 3,061 lines and `sm70_encode.rs` 4,846;
  ours cover only the kernels we emit, plus scheduling and register use.
- Display and 3D: the least mapped; designed at stage 7.

## Unknowns only hardware settles

The 4060 Ti:

1. Whether its VBIOS FWSEC descriptor is v2 or v3, and whether FRTS succeeds
   with our layout.
2. Whether a cold UEFI boot needs the scrubber first.
3. Whether the GOP framebuffer keeps scanning out through FWSEC, booter and
   GSP init.
4. Whether GSP-RM accepts `GspSystemInfo` without real ACPI data.
5. Warm-reboot behaviour with WPR2 still up.
6. Whether every CPU-sequencer opcode this board sends is in nouveau's set.
7. The timeouts for `GSP_INIT_DONE` and the golden-context RPCs.
8. Whether NAK's HMMA encodings give correct answers on AD106.

The 970:

9. Whether our WPR and ACR bootstrap is accepted by the signed image on this
   board's fuse revision.
10. The yield bit's polarity, and SM 5.2 stall counts beyond maxas's tables.
11. The clocks its VBIOS leaves, and therefore its throughput.
12. Behaviour on the 970's slow 0.5 GB memory segment.

## Open

**Boot allocation:** on 2026-09-30, the successful host fixture plus boot
sequence and RPC serialization allocated 83,096 bytes before trace
formatting, under seed `561EEBFC3ED59D96`. Both tested DMA-size profiles had
the same allocation. This is not full peak usage or isolated driver cost.
`NvGspSysInfo` builds its fixed 928-byte payload in one zeroed raw buffer,
writes little-endian fields and converts once to the returned byte list.
Construction takes linear time and storage in payload size; caller heap
ownership includes the raw temporary and returned list. Boot control takes
time linear in DMA chunks plus backend polling and does not accumulate
per-chunk event lists. The fixture uses a bounded raw trace buffer and
restores its per-case heap after printing; its recursive hex formatting
also copies growing strings. Establish complete boot lifetimes, peak usage
and the hardware memory budget during integration.

**The firmware licence** (decision 3 stands): `LICENCE.nvidia` 2.1.2 allows
redistribution only with an OS under an OSI-approved licence, and the
repository states none. Until that is settled, both cards' firmware is read
from the box, never from the depot or a shipped image.
