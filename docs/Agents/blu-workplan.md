## The annotation extraction tool (Damian, 2026-08-04)

Two phases with a human audit between them, which is how he asked for it:
"one produces the report, then you manually audit the report for false
positives, edit the report, then run the report->codemut transform."

`build/extract-annotations.ps1` is phase one and is READ ONLY. It cuts
column-2 prose into blocks, names the definition each sits against
(`chapter:`/`section:`/`type:`/`function:`), proposes a verdict and writes
`docs/Reports/AnnotationExtract.txt`.

**It never proposes DELETE, on purpose.** Whether a block explains our own
code is a judgement, and a keyword classifier answering it would be an
instrument that cannot fail: every block gets an answer and nothing says which
answers are wrong. So the proposal is KEEP or ANNOTATE, the worst automated
outcome is prose moved to a sidecar rather than lost, and DELETE is a word only
the auditor writes.

`build/apply-annotations.ps1` is phase two and is the only half that mutates.
Every block carries its source verbatim in the report; a block whose lines no
longer match is refused **per FILE, not per block**, because applying only the
blocks that still happen to match would cut the right lines out of the wrong
places. Nothing is written without `-Apply`; `-List` prints the files to
`p4 edit` first, since a Write to a Perforce read-only file throws.

**Measured 2026-08-04 over the tree, pattern `^ [^ ]`:** 3,349 chapters, 2,698
with prose, 14,539 blocks, 66,844 prose lines, 4,814 KEEP and 9,725 ANNOTATE
proposed, 1,584 `We say:` markers excluded. 4.6 s. **State the pattern beside
that count**: this file previously said 54,912 lines across 2,640 of 3,292
chapters and `CLAUDE.md` says 64,450 across 2,601 of 3,249; all three counted
different things and none of them said what.

Verified end to end in an isolated scratch repo rather than on the tree: KEEP
left in place, DELETE cut with nothing kept, ANNOTATE moved to a JSON ARRAY
sidecar with the right target and kind, blank runs collapsed so extraction
leaves no widening gap, and a stale report refused with the source untouched.

**Next: the audit.** The report exists and nothing is applied. 9,725 ANNOTATE
proposals are the thing to read, and the ones to look at first are the
`| none` signal rows, which are what the classifier could say nothing about.

**`ScForLoop` is a trap and it is why both generators use `ScWhile`.** Its step
is a bare ShellExpr and there is no increment node, so `(SeAdd (SeVar "x")
(SeInt 1))` emits `for (...; ...; ($x + 1))` -- an expression that computes and
never assigns, which is an infinite loop that parses clean. Every existing
caller in the tree passes `SeRaw "$i++"`. A `while` with a trailing
`ScIncrement` is raw-free and correct, but it cannot carry a `ScContinue`,
which would skip the increment.

**PowerShell scoping ate every counter on the first run.** A `$count++` inside
a generated `function` writes a function-local copy, so the summary printed
`0 chapters, 0 blocks` over a report full of records. `ScAssign`/`ScIncrement`
take the name as Text, so `"script:blockCount"` spells the scope with no new
DSL node. **Read the COUNT in a summary line, not just its verdict** -- the
verdict was right while every number beside it was zero.

**Terminal colour is modelled as the sixteen named colours, NOT as an
`Rgb`, and that was checked before it was chosen.** The forewords do carry
colour -- `Foreword/game/Color.codex` (RGB, HSL, palettes, lolcat) and
`Punctual/ColorOps.codex` (packed ARGB) -- but both are PIXEL colour and
the tree contains no ANSI SGR at all. A console takes a ConsoleColor, not a
triple, so the sixteen are the portable intersection of ConsoleColor, ANSI
SGR and the Windows attribute nibble. **PowerShell's names sit one
intensity below ANSI's**: its `Red` is ANSI bright red, ANSI red is its
`DarkRed`, its plain white is `Gray`. So PowerShell `Cyan` is
`ClBrightCyan` here, and writing `ClCyan` silently darkens the output. A
truecolor variant taking an `Rgb` fits later under Damian's rule, emit if
we can and ignore if we cannot: PowerShell would ignore it, ANSI would
render it.

**THREE emitter defects of the same family have now been found, and expect
more.** All were correct-by-accident and all were invisible until a script
happened to exercise the shape.

1. `SeConcat` emitted `(a + b)`. Fine until an integer was leftmost, then
   PowerShell parses the right as a number and throws.
2. `emit-ps-args` space-separated arguments for BOTH commands and methods.
   Fine until a `.NET` call took more than one argument, then
   `WriteAllText($a ($b) $c)`. **Fixing it moved 19 untouched generators
   closer to their targets**, so some of the 6300 drifted lines were never
   the generators' fault at all.
3. `ps-quote` emitted literals double-quoted with **no escaping at all**.
   Fine until a literal contained a quote, then
   `$inject = "<link rel="stylesheet" ...>"`, a parse error. Literals are
   single-quoted now, which also removes every interpolation risk from a
   `$` or a backtick inside a literal.
4. `SeStaticCall` and `SeStaticProp` emitted a bare `[Type]::Member`, which
   PowerShell refuses in COMMAND-ARGUMENT position: `Join-Path
   [System.IO.Path]::GetTempPath() $x` does not parse. Fine for as long as
   every static call sat in an assignment or inside a method call's own
   parentheses. Both are parenthesised now.
5. `SeIfElse` emitted `(if ...)`. PowerShell's parentheses take an
   expression and `if` is a statement, so this **parsed clean** and died at
   run time with "the term 'if' is not recognized", having been read as an
   attempt to run a command called `if`. The subexpression form `$( )` takes
   a statement. **This one is the reason parsing is not sufficient
   verification: run the generated script.**

**When a conversion produces odd-looking output, suspect the emitter before
the generator, and ask whether the shape has simply never been exercised.**
The corollary is that the drift figures are not a pure measure of generator
staleness: fixing an emitter moves scripts nobody touched, in both
directions, and quoting style in particular is cosmetic. Do not read a drift
delta as progress without knowing which of the two moved.

**`SeConcat` had been working by accident and no longer does.** It emitted
`(a + b)`, but PowerShell's `+` only concatenates when the LEFT operand is
already a string; an integer on the left parses the right as a number and
throws. Every converted script was correct only because its author put a
string literal leftmost, and the first one that did not
(`compliance-report`'s closing line, `($lines + " lines)")`) was a runtime
crash on the last statement of an otherwise passing run. It emits
`([string]a + b)` now. **The general lesson is the one to carry: a node whose
correctness depends on the order the author wrote its operands is a node
that will break later, so fix it in the emitter rather than in the caller.**

**Why they rotted, measured rather than guessed.** The DSL had the structure
(`ScIf`, `ScTry`, `ScMkdir`) but no vocabulary for what build scripts do, so
authors reached for `ScRaw` and then the generator was worth less than the
`.ps1`. Across all 49: 2665 raw literals, 873 command calls, 95 distinct
cmdlets, but a steep head. `Add-DirEntry`, `Measure-Phase`, `Stop-VmGraceful`,
`Close-Vm`, `Start-VmRun`, `Read-StreamLine` and `Write-SweepLog` are not
PowerShell at all, they are helpers the scripts define, which is what
`ScFunction` was built for in increment 2.

**Keep the nodes intent-level anyway, with parity dropped.** `ScCopy` and
`ScMkdir` say what is meant; `ScRun` and `ScRaw` are PowerShell wearing a
Codex costume. The reason survives the ruling: the point is that the LOGIC
lives in the AST rather than in PowerShell text, and a node whose meaning is
a cmdlet invocation has not moved the logic anywhere.
