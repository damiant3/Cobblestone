## Signature verification hardening

- **Ed25519 refuses small-order keys and points**: `ed25519-verify` accepted a small-order A or R, so an unsigned CDX passed the seed and image checks for one content hash in four. A and R whose [8]P is the identity are now refused; the arms grade all four h classes, 8 small-order points as A and as R, S = L, non-canonical encodings, RFC 8032 and the 151 Wycheproof vectors, and the pre-fix verifier accepts the h = 3 class and all 8 small-order A rows (red 38145, seed 279DF926; caller arm blu 38189). Every public update from 30 through the Update 67 preview shipped the flaw.
- **The project signer is pinned**: the seed gate, the desk's seed check and the chain loader verified a CDX under the key in its own header, so any freshly re-signed image passed. `seed/signer.pub` now compiles into `CdxBinary` as `cdx-signer-key`, `cdx-signed-by-project` refuses any other header key, and `test-self-verify.ps1` reports the seed verifies itself only when pinned (red 38219).
- **RSA modulus floor**: a signature under a 512-bit or 1024-bit RSA key verified, in X.509 chains and TLS CertificateVerify alike; moduli under 2048 bits are refused, graded against .NET CNG keys (red 38192).
- **X.509 constraints**: only the cA bit was read, so a CA under a pathLen 0 issuer, an issuer without keyCertSign, a leaf outside critical nameConstraints and a certificate with an unknown critical extension all verified. Unknown critical extensions are refused at parse and the chain walk enforces keyCertSign and pathLen, the same four refused by .NET X509Chain (red 38200).
- **Revocation authority**: any key could revoke any identity, content or capability. An identity record is admitted only from that identity's key or the project signer, and content, capability and vault records only from the project signer (blu 38230).
- **Agent bundles and browser publishers**: an agent manifest was verified under its own key, which authenticates nobody; it now must be a trusted author's key (reek 38240). A page with no publisher header verified, and the page loader never consulted its trust store; both now refuse (reek 38240). Fetched page digests are kept as 32 octets and both signature headers are hex-decoded, so a signed remote page verifies end to end (reek 38295).
- **Market passwords**: one HMAC keyed by the store's id, compared as text with an early exit. Passwords now use PBKDF2-HMAC-SHA256 at 20000 iterations with a per-user salt and a full-length compare, and legacy records migrate at login (val 38210); 20000 is bounded by the PBKDF2 cost on codex-vm, 0.38 to 0.48 s per verify (val 38222).
- **CodexMagic accounts and chain**: sessions were predictable (the first admin's token was `s1000`), passwords plain text, the server state publicly dumpable, and signature verify and clan authorize never checked their inputs; sessions are keyed, passwords digested, the dump removed and both checks refuse (blu 38321). Chain transactions carried a toy two-word "signature" anyone could forge with key 0; they are now Ed25519 over every field against a key registered once per account (val 38344), and a nonce must exceed the sender's last, so a mined or pending transaction replayed is refused (val 38346).
- **UOAIX character delete**: an empty creation password let an empty delete password through, compared as plain text. Delete now verifies the account password through PBKDF2, and creation no longer stores the character password (val 38337).
- **Found by the census**: `ServiceProxy`'s policy check had never compiled since its first revision (fester 38318); Spark `Brush` and `BrushEngine` compiled only inside `App`'s unit, which hid two type errors in `ImageTool` (fester 38331).
- **Audited and clean, with arms**: ECDSA P-256 and P-384 degenerate keys and signatures (reek 38124), X25519 low-order points (reek 38169), the AEAD and MAC tag compares, HKDF, PBKDF2 stored records, the TLS, DTLS and admin HMAC callers, and the SHA family against .NET at every padding edge; the C2SP Wycheproof ECDSA P-256 (262), RSA 2048 (259) and X25519 (518) suites agree with every verdict (reek 38206).
- **The after-action report and its runner**: the story of how `Ed25519.codex` passed its one validation (it implemented RFC 8032's invalid-input list, which permits small-order points), the census by behaviour, lesson L-SPECCEILING, and `build/checks/degenerate-arms.ps1`, which lists 63 foreword trust decisions and which of them carry a degenerate-input arm (fester 38143, 38248).
