# Backlog — Open Capabilities

**Updated**: 2026-07-16

## This is not a status doc

It is the register of what Codex is supposed to be able to do and cannot
do yet. **Open work only.**

- **When you close an item, DELETE the entry.** Do not mark it done, do
  not leave a summary of how you closed it, do not leave a tombstone.
- **The history is in Perforce.** The changelist that closed the work is
  the record — it has the diff, the description, the date and the author,
  and it cannot drift. Status, dates, agent names, CL numbers and the arc
  of how the work went all belong there, not here.
- **An entry says what is still missing, and nothing else.** If a sentence
  would still be true once the gap is closed, cut it.
- **A `Deferred` entry is a real gap that is deliberately not being worked
  yet.** It keeps its place in the register because it is true. The marker
  says only that the decision to wait has already been made: do not
  re-derive it, do not lead a status report with it, do not re-open the
  question of whether it matters. Take the marker off when the easier work
  is done and it is next.

The one thing that is never deleted is a gap that is still real. See rule
1 — that mistake has already been made in this file, and it cost more than
every stale entry in it combined.

## Three rules, each learned the hard way

1. **A capability we want is never quietly deleted.** If a claim turns
   out to be false, the entry gets *louder*, not smaller. An empty
   backlog would mean we had stopped being honest, not that we had
   finished. Deleting a true gap is the one unrecoverable mistake in doc
   work — two were nearly lost in the 2026-07-13 reconciliation because
   they were confidently reported as false. They were real.

2. **An entry that *adds* a todo deserves the same scrutiny as one that
   *deletes* a capability.** Four §1 entries were once filed from a
   subagent sweep and were simply wrong — one of them invented a coverage
   gap from a *filename*. The first kind of error wastes a day; the second
   loses the gap forever. Neither is free. **Read the code. Do not infer.**

3. **An entry that outlives its gap is not harmless.** A shipped
   capability still listed as open invites the work to be done twice —
   that is how a second, redundant trust gate got built and thrown away.
   Re-read the source before you trust a line in this file, including
   this one.

## 3. Codegen and backends

| # | Capability | State of the gap |
|---|---|---|
| 3.1 | **ARM64 register allocator** | No general allocator was ever built. Registers are recycled ad hoc per site, and retargeting is *hard-disabled* (`a64-can-retarget-last` returns `False`) purely because nothing makes it safe. This is the last real architectural hole in the codegen. Design (still valid): `docs/Designs/Active/Compiler/Arm64RegisterAllocator.md`. **2026-07-14: this closes into the middle-end LIR workstream (3.8, step 5) — the LIR lives in `IR/` as a citable chapter with the register file as data, so the same linear-scan allocator serves x86-64 and the ARM64/RISC-V plugs. Do not build a standalone ARM64 allocator.** |
| 3.3 | **SIMD Phase 2: AVX / AVX2** | Phase 1 (SSE2, 128-bit) shipped. There is no VEX encoding and no YMM register pool. Doubling lane width benefits every existing vector path. |
| 3.4 | **The SPIR-V validator checks types and dominance, and a kernel runs on a real driver** | `spv-validate` is structural only — ids, references, layout. It does not check that an instruction's operands agree in type, and does not check dominance. And no SPIR-V module has ever been handed to a Vulkan driver: there is no runtime in the tree, so "the SPIR-V backend works" rests on our own reader agreeing with our own writer. |
| 3.5 | **RV32 and Thumb-2 codegen** | The encoders exist; the codegen does not. These are the actual MCU-class targets, and Thumb-2 is the *only* way the Cortex-M board drivers ever run on silicon. |
| 3.6 | **Cross-arch battery is honest and gated** | ARM64 runs 132 pass / 2 fail under the committed Renode board (the "135/135 parity" claim was wrong and is still quoted in places). Fix the two, then decide whether the cross-battery becomes a `build.ps1` leg or stays an out-of-band tier. **There is no cross-arch EXECUTION gate today** — `build.ps1`'s `plug-binary` leg builds the riscv/arm64 plugs (a compile gate) but nothing runs a cross-arch battery. |
| 3.7 | **PTX transcendentals use libdevice** | `ptx-emit-sincos` lowers sin/cos/tan through a cvt-to-f32 sandwich (`sin.approx.f32`), so a `Real` transcendental silently loses f64 precision on the GPU. Only sin/cos/tan — `sqrt` emits native `sqrt.rn.f64`, and exp/log are not sandwiched because they do not exist. |
| 3.8 | **The middle end reaches the emitted binary** | **The LIR exists and is dead.** LIR-1..7 shipped (`codex/compiler/IR/Lir.codex`): flat LIR, lowering, blocks, liveness, an allocation verifier, a Wimmer linear-scan allocator. A pass manager is live (`Passes.codex`, `default-ir-pipeline` = fold-constants, inline-leaf-calls). **The LIR is reachable only through an opt-in `lir-dump`: there is no x86 selector, so not one emitted byte has moved.** The gap is the selector — until it lands the allocator is a library nothing calls, and 3.1 (ARM64 allocation) closes into it rather than being built standalone. Second half: range analysis at the emit boundary is per-expression (`ir-expr-proven-range`, `X86_64Compound.codex`) — `IrLet` discards the bound's proven range and `IrName` falls to the default, so a bound proved at a binding is lost at its use. Design: `docs/Designs/Active/Compiler/LIR.md`. |

| 3.9 | **CDX codegen eliminates dead code** | It does not. **Every top-level definition in the compilation unit is emitted, whether or not it is reachable** from the program's entry point — so a chapter that is present but uncalled is compiled into the binary in full. Surfaced 2026-07-14: the middle-end occurrence analyser (`IR/Occurrence.codex`, reachable only through the opt-in `occ-report` pass) added **~11 KB of code to the seed that nothing calls from `opening`**. **The reachability machinery already exists** — `ir-prune-unreachable` (`Emit/IRTextEmitter.codex:649`) is a flood-fill DCE from a named root — but it is applied **only to IR-text output for the plugs** (`opening.codex:1477/1497`, root `"opening"`), never to CDX emit. **This is NOT a wire-it-in one-liner, and that is the entry:** the compiler reaches code indirectly — effect handlers through the dispatch table, the REPL loop, functions reached only via builtin dispatch — so `opening` alone is an insufficient root set, and a naive flood-fill over CDX would drop functions that run at runtime and ship a broken compiler. Whole-program DCE needs a *correct conservative root set* (every entry point, every indirectly-dispatched handler), and that root-set analysis is the work. It is a middle-end capability and belongs to 3.8's campaign; until it exists, an unreachable helper is dead weight in the root-of-trust seed. |

| 3.2 | **ARM64 frame elision for plain leaves (deprioritised -- revisit; the gate is not the fix)** | The win is real: a frameless path exists but `a64-can-be-frameless` requires `a64-should-tco`, so it only applies to self-recursive functions -- an ordinary call-free leaf still pays `SUB SP, SP, #96` + `STP fp,lr` + the epilogue `LDP`/`RET` (ARM64 has no stack guard to also elide, unlike x86-64). **Attempted 2026-07-15 (blu) and REVERTED -- do NOT just widen the gate.** Broadening `a64-can-be-frameless` to accept plain leaves (no non-tail call, <=8 params, <=6 estimated locals, excluding `opening`) makes simple leaves frameless *correctly* -- `square (n) = n*n` went from a full frame to `mov x9,x0; mul x0,x9,x9; ret` (3 insns) -- but it MISCOMPILES specific leaf shapes: `chacha20poly1305`, `aesgcm256` and `cce-tier1` regressed (verified: all three pass on the baseline plug, fail with the change), while `arithmetic`/`factorial` stay correct. Three hypotheses were built and disproved by rebuild-and-measure: **(1) register overflow** -- a leaf needing >6 locals runs the frameless allocator into callee-saved x19-x27 (unsaved by the frameless path) or spills to unallocated stack, since `a64-alloc-local` only spills past x27. Added speculative-frameless-then-fall-back-to-framed keyed on `spill-count`/`peak-local` (the fallback is clean: re-emitting from the *original* state overwrites the in-place code buffer at the same `code-pos`, and the func offset is recorded once). It did not fix the failures, and exposed that the guard was inert because `a64-reset-func-state` sets `peak-local = x19`. **(2)** Reset `peak-local` to x9 so the guard actually tracks usage -- still failed, so **overflow is not the cause.** **(3)** The frameless emitter hardcodes `tco.active = True, in-tail-pos = True` (correct for a TCO loop, wrong for a plain leaf, which would TCO-mangle the tail expression) -- set it from `a64-should-tco` instead -- **still failed.** So it is a narrow, shape-specific miscompilation in `a64-emit-function-frameless`'s expression/register handling that no gate can screen out. **The real fix:** bisect ONE crypto helper (e.g. inside `aesgcm256`) to the exact miscompiled leaf, disassemble frameless vs framed for it, and fix the frameless emitter -- not `a64-can-be-frameless`. The payoff (frame elision on every plain leaf, thousands of them) is worth it; it is a deeper emitter fix, not a quick gate change, which is why this now sits at the bottom of the list. |

| 3.10 | **The text emitter round-trips all valid source** | The semantic-equivalence gate (`build.ps1` phase 6) re-emits the source in TEXT mode and compares every definition body. Two valid source shapes do not survive that round-trip. (1) Redundant parentheses: the emitter drops them (correctly), but when the SOURCE carries them the body comparison flags a mismatch -- source `((iv.start) == (0 - 1))` re-emits as `(iv.start == 0 - 1)`. (2) Prose wedged between a type signature and its definition does not round-trip. Surfaced 2026-07-17 by the LIR selector: 3 functions (`lir-alu-imm`, `lir-iv-insn`, `lir-scan-step`) failed the gate and were worked around in the LIR source (relocate the prose above the sig; write comparisons in the emitter's canonical paren-free form). The gap: the emitter or the comparison's normaliser should treat these as equivalent so valid source is not rejected by the compiler's own round-trip. Low priority -- the normaliser stripping redundant parens is the cheap fix. |

| 3.11 | **Integer division rounds consistently for negative dividends** | A power-of-two divisor lowers to a shift/mask (floor: `-7 / 2` = -4); every other divisor lowers to `idiv` (truncate toward zero: `-7 / 3` = -2). So plain `Integer` `/` floors or truncates depending on whether the divisor is a power of two, for negative dividends only. Both the tree emitter and the LIR selector do this identically -- it is a language-level inconsistency, not a codegen regression. The language should pick one rounding rule for `Integer` division and make both lowering paths honour it. Found 2026-07-17. |

## 7. Test and quality debt

### How the app debt is worked (Damian, 2026-07-14)

**The apps battery is deliberately not run.** It costs a full hour, there
are no customers, and nobody is complaining. The bugs will keep. Do not
run it, and do not treat its failure count as a number this project owes
anyone.

**Attack the app debt by BREAKAGE CLASS, not app by app.** The apps are
not N broken programs; they are a handful of mechanical breakages
repeated across N programs, because the language moved and the apps did
not. Filed per-app, the same defect gets diagnosed five separate times —
which is exactly what happened to `[Console] None` (found in `apps/works`,
fixed there, and left standing in seven other entry points). Filed as a
class, it is one grep and one sweep.

So: **fix what we see, and when you see it, lift the whole class.**
